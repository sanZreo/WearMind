**采用的整合策略（方案 A）**：把本地提交直接叠在远程提交之上，而不是两次根提交再合并。

实际执行只用了两条命令：

```bash
git update-ref refs/heads/main origin/main   # 分支指针指向远程提交
git commit ...                                # 暂存区已有 91 条，直接提交
```

> **与预案的一处修正**：预案里还包含 `git read-tree HEAD`。执行前发现暂存区已有 91 条 staged 记录，
> 而 `read-tree HEAD` 会把索引重置成远程树（只剩 `README.md`），等于清空已完成的暂存。
> 因此**跳过 `read-tree`**。`update-ref` 既不碰工作区也不碰索引，是更小侵入的正确做法。
> 结果证明：README.md 在暂存区表现为 `M`（修改），其余 90 个为 `A`（新增），正是期望状态。

未使用 `--allow-unrelated-histories`，未产生 merge commit，未做历史重写。

**故障一：`github.com` 的 DNS 解析到了一个不可达 IP**

| 目标 | 结果 |
|---|---|
| 本机 DNS 返回 `github.com` → `20.205.243.166` | ❌ 连接超时（直连与经代理均失败） |
| `140.82.112.3` / `.113.3` / `.114.3` / `.121.3` | ✅ 全部 HTTP 200 |
| `api.github.com` / `codeload.github.com` / `objects.githubusercontent.com` | ✅ 正常 |
| `example.com` / `baidu.com`（对照组） | ✅ 正常 |
| 环境代理 `127.0.0.1:6349` 对 `github.com:443` | ❌ `CONNECT tunnel failed, response 502` |

结论：**不是网络封锁、不是仓库权限、不是认证问题，而是单一域名的 DNS 答案指向死 IP。**

处置：未修改 hosts、未改系统代理、未降级 TLS 校验。改为启动一个**临时本地 CONNECT 隧道**
（监听 `127.0.0.1:18080`，仅将 `github.com` 定向到可用 IP，其余域名按正常 DNS 解析）。
TLS 仍为端到端，SNI 与证书校验均针对真实域名 `github.com`，**未使用 `sslVerify=false`**。
推送完成后隧道进程已停止，仓库配置中**未残留** `http.proxy`。

`credential.helper` 为 `manager`（Git Credential Manager），但 Windows 凭据管理器中

授权后凭据由 GCM 接管，后续推送无需再次输入。

### H.1b 复发风险与长期修法

DNS 指向死 IP 是**本机网络环境问题**，会再次影响后续 push。三种长期方案：

1. **更换 DNS**（最省事）：网卡 DNS 改为 `223.5.5.5` / `1.1.1.1`，使 `github.com` 解析到可用 IP；
2. **写 hosts**（需管理员）：加一行 `140.82.113.3 github.com`。**本次未执行**，属系统级改动；
3. **用代理/加速器**：开启后直接 `git push`，无需任何额外参数。

在此之前，本机推送前需确认 `github.com` 可达：

```powershell
curl.exe -sS -o NUL -w "%{http_code}`n" --max-time 10 https://github.com/
```

返回 `200` 即可直接 `git push`；超时或 `000` 则先用上述任一方案。
