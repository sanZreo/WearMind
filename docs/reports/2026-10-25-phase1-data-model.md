## B. users 和 items 的字段、索引、外键设计

### users

| 字段 | 类型 | 约束 |
|---|---|---|
| `id` | `BIGINT` | PK，`GENERATED BY DEFAULT AS IDENTITY` |
| `public_id` | `UUID` | `NOT NULL`，`UNIQUE`，`DEFAULT gen_random_uuid()` |
| `display_name` | `VARCHAR(64)` | `NULL` |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL`，`DEFAULT now()` |
| `updated_at` | `TIMESTAMPTZ` | `NOT NULL`，`DEFAULT now()` + ORM `onupdate` |

索引：`pk_users(id)`、`ix_users_public_id(public_id)` **UNIQUE**

**为什么用两个 ID**：`id` 是内部主键，整数外键体积小、索引紧凑；`public_id` 是对外标识，
避免暴露自增 ID（会泄露用户总量与注册顺序，也便于枚举）。

### items

| 字段 | 类型 | 约束 |
|---|---|---|
| `id` | `BIGINT` | PK，IDENTITY |
| `user_id` | `BIGINT` | `NOT NULL`，FK → `users.id` **ON DELETE CASCADE** |
| `name` | `VARCHAR(120)` | `NOT NULL`，`CHECK length(btrim(name)) > 0` |
| `category` | `VARCHAR(32)` | `NOT NULL`，`CHECK IN ('top','bottom','outerwear','dress','shoes','accessory','other')` |
| `color` | `VARCHAR(32)` | `NULL` |
| `image_ref` | `VARCHAR(512)` | `NULL`（只存存储引用，不存 URL / 二进制） |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | `NOT NULL` |

约束名（由命名约定生成，可稳定引用）：

- `pk_items`
- `fk_items_user_id_users` — `FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE`
- `uq_items_user_id_id` — `UNIQUE (user_id, id)`
- `ck_items_category_valid`
- `ck_items_name_not_blank`

索引：

- `ix_items_user_id_category (user_id, category)` — 支撑"某用户的某类衣物"
- `uq_items_user_id_id (user_id, id)` — 同时充当 `user_id` 前缀索引，**因此不单独建 `ix_items_user_id`**（那会是纯冗余，只增加写放大）

**三个刻意的设计选择**：

1. `UNIQUE (user_id, id)` 不是多余的 —— 它让将来的子表（`item_images` 等）能用
   `FOREIGN KEY (user_id, item_id) REFERENCES items (user_id, id)`，
   从数据库层面保证"子行与父行属于同一用户"，而不是靠开发者记得加过滤。
2. `category` 用 VARCHAR + CHECK 而非原生 ENUM：ENUM 加值要 `ALTER TYPE`，Alembic 不自动生成，回滚困难。
3. `color` / `image_ref` 允许为空：文字添加衣物时可能没有颜色、先建档后补图是正常流程。

## E. 数据隔离测试的覆盖范围与局限

### 已验证（数据库层面真实有效）

1. 两个用户可以各自拥有衣物，互不干扰；
2. 按 `user_id` 过滤的查询只返回该用户的衣物（名称集合与归属同时断言）；
3. 每件衣物确实归属其创建者，B 的衣物不会挂到 A 名下；
4. 按用户分组计数与实际情况一致（没有凭空多出或无主记录）；
5. 外键有效：`user_id = 999999999` 被数据库拒绝（`IntegrityError`）；
6. `ON DELETE CASCADE` 有效：删除用户后其衣物计数归零；
7. `CHECK` 有效：非法类别 `spacesuit`、全空白名称 `'   '` 均被拒绝；
8. `public_id` 由数据库生成，是合法 UUID 且互不相同。

### 明确不能证明的事

> 这些测试里 `user_id` 是**测试代码显式传入**的。

因此本阶段证明的只是"模型关系 + 外键 + 带过滤的查询"是通的。真实系统里 `user_id`
必须来自**可信认证上下文**，绝不能来自请求参数。以下**全部未实现**：

| 层次 | 需要的措施 | 状态 |
|---|---|---|
| 访问层 | 仓储方法签名强制接收 `UserContext`，`user_id` 不从参数取 | ❌ 未实现 |
| 接口层 | 从认证上下文解析当前用户 | ❌ 未实现 |
| 接口层 | 越权访问返回 404/403 | ❌ 未实现 |
| 测试 | 越权用例（A 持 B 的 `item_id` 请求） | ❌ 未实现 |

**在认证与仓储层落地前，不能声称系统具备完整的多用户隔离能力。** 这一点已写入
`docs/design/phase1-users-items.md` 第 0 节与测试文件 docstring。

## F. 未完成的问题和风险

### F-0 【已修复，但值得记录】`.gitignore` 曾把 ORM 模型目录一并忽略

Phase 0 写的 `.gitignore` 里有一条 `models/`，本意是忽略**根目录**下的模型权重文件。
但在 gitignore 语法中 `models/` 会匹配**任意层级**的同名目录，
于是 `apps/api/app/models/` 整个被静默排除。

后果的严重性：`git status` 里完全看不到这 4 个文件，如果直接提交，
**代码在本地能跑、推上去就缺了整个模型层**，而且不会有任何报错。

发现方式：核对新增文件清单时注意到 `app/models/` 没出现，用 `git check-ignore -v` 定位到
`.gitignore:58`。已改为 `/models/`（仅根目录），并复验：

- `apps/api/app/models/*.py` → `tracked-ok`
- 根 `models/x.gguf` → 仍被忽略

教训：**gitignore 里凡是目录名，一律加前导 `/` 锚定根目录**，除非确实想匹配所有层级。

### F-1 【已处置，但必须记录】连接串曾被误打印

在检查库表时，我把 SQLAlchemy 风格的 URL（`postgresql+psycopg://`）直接传给了
`psycopg.connect()`，它解析失败并把**含密码的完整连接串打进了异常信息**，输出到了终端。

处置：立即用 `ALTER ROLE wearmind PASSWORD` 轮换该角色密码，同步更新
`var/secrets/pg-wearmind.txt` 与 `apps/api/.env`，并复验新密码连通。
**被打印的密码已失效**，泄露面收敛。

已把根因写入项目长期记忆：必须先用 `sqlalchemy.engine.make_url()` 拆字段再传给 psycopg。

### F-2 认证完全缺失（最大的业务风险）

`users` 表没有任何认证字段；`items.user_id` 目前可由调用方任意指定。
在 Phase 2 完成"从可信上下文取用户 + 仓储层强制过滤 + 越权测试"之前，
**任何暴露给外网的接口都可能发生越权**。

### F-3 `updated_at` 不是数据库触发器

经 ORM 的更新会刷新；绕过 ORM 的批量 SQL / `psql` 手工改数据**不会**刷新。
第一版接受该取舍，需要时再加 `BEFORE UPDATE` 触发器（独立迁移）。

### F-4 测试数据库策略的局限

- 测试跑在**开发库**上（`wearmind`），靠外层事务回滚保证不落数据。
- 好处：不需要额外建库、不需要给角色 `CREATEDB` 权限。
- 风险：若将来某个用例用 `connection.commit()` 或 DDL（会隐式提交），隔离就会失效。
  届时需要独立的 `wearmind_test` 库 + 迁移应用。

## G. 下一阶段建议

按依赖顺序，Phase 2 建议聚焦"认证 + 仓储层"，因为越权风险目前是敞开的：

1. **仓储层先行（不需要认证也能做）**：
   `ItemRepository(session, ctx: UserContext)`，所有查询强制 `WHERE user_id = ctx.user_id`，
   让"忘记加过滤"在类型层面难以发生；配套单元测试。
2. **认证最小实现**：单用户开发模式（固定 `DEV_USER_ID`）+ 预留 `UserContext` 注入点，
   先不引入 JWT/密码体系，避免过早背负复杂度。
3. **越权测试**：A 持 B 的 `item_id` → 必须 404（不是 403，避免泄露资源存在性）。
4. **衣物 CRUD API**（无图片）：`POST/GET/PATCH/DELETE /api/v1/items`，
   加 `contracts` 类型生成，前端衣柜页接上。
5. **Alembic 多版本演练**：加第二个迁移（如 `item_images`），验证 `upgrade`/`downgrade` 链式回滚。

不建议现在做的：图片上传（要先定存储与脱敏流水线）、Agent、LLM 接入。
