# Phase 1：users / items 数据模型设计

- 日期：2026-10-25
- 状态：已实现并迁移（revision `6efff137cb6c`）
- 范围：**仅数据模型与约束**。不含认证、不含衣柜 API、不含图片上传

---

## 0. 必须先读的一条限制

> **本阶段的 `users` 表不代表系统已具备认证能力。**

表里没有任何密码、令牌、会话、OAuth 字段 —— 因为这些还没有设计，先造出半成品比没有更危险。

`items.user_id` 目前由调用方传入。**真实 API 接入后，当前用户必须从可信认证上下文
（如经校验的签名会话 / JWT 的 `sub`）获得，绝不能接受客户端传入的 `user_id`。**
否则攻击者只要把 `user_id` 换成别人的，就能读写他人衣柜。

相应的防护要在 Phase 2 落地：

| 层次 | 措施 | 本阶段状态 |
|---|---|---|
| 建表 | `user_id NOT NULL` + 外键 + 索引 | ✅ 已实现 |
| 数据库 | `UNIQUE (user_id, id)` 供复合外键使用 | ✅ 已实现 |
| 访问层 | 仓储方法签名强制接收 `UserContext`，`user_id` 不来自参数 | ❌ 未实现 |
| 接口层 | 从认证上下文取用户；越权访问返回 404 | ❌ 未实现 |
| 测试 | 越权用例（A 拿 B 的 item_id） | ❌ 未实现 |

## 1. 表关系

```
users (1) ──── (N) items
        └─ ON DELETE CASCADE
```

刻意只建这两张表。`user_profiles`、`item_images`、`item_attributes`、`outfits`、
`suggestions`、`feedback`、`preferences` 等按架构文档 B.3 后续再加 —— 现在建它们
只会得到一堆没有业务逻辑支撑的空壳。

## 2. `users`

| 字段 | 类型 | 约束 | 设计理由 |
|---|---|---|---|
| `id` | `BIGINT` | PK，`GENERATED BY DEFAULT AS IDENTITY` | 内部主键。用整数而非 UUID：`items` 会快速增长，`BIGINT` 外键比 `UUID` 小 4 倍，索引更紧凑 |
| `public_id` | `UUID` | `NOT NULL`，`UNIQUE`，`DEFAULT gen_random_uuid()` | **对外**暴露的标识。不暴露自增 ID，避免泄露用户总量与注册顺序、降低枚举风险。默认值由数据库生成，应用不必关心 |
| `display_name` | `VARCHAR(64)` | `NULL` | 展示名。允许为空：注册流程尚未实现，此时留空比编造默认值诚实 |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL`，`DEFAULT now()` | 由数据库生成，规避应用时钟漂移 |
| `updated_at` | `TIMESTAMPTZ` | `NOT NULL`，`DEFAULT now()` + ORM `onupdate` | 见 §5 已知取舍 |

索引：

- `pk_users (id)` —— 主键
- `ix_users_public_id (public_id)` **UNIQUE** —— 按对外标识查用户，是 API 层唯一会用到的查询路径

为什么用 `BIGINT IDENTITY` 而不是 `serial`：`serial` 是 PG 的历史语法，
`GENERATED BY DEFAULT AS IDENTITY` 是 SQL 标准写法，权限与序列归属更清晰。

## 3. `items`

| 字段 | 类型 | 约束 | 设计理由 |
|---|---|---|---|
| `id` | `BIGINT` | PK，`IDENTITY` | 同上 |
| `user_id` | `BIGINT` | `NOT NULL`，FK → `users.id` `ON DELETE CASCADE` | **衣物必须属于某人**。`CASCADE` 对应架构文档「删除账号 → items 全部清除」的要求；同时也意味着不存在无主衣物 |
| `name` | `VARCHAR(120)` | `NOT NULL`，`CHECK length(btrim(name)) > 0` | 120 字符足够描述「米白色 oversize 针织开衫」这类名称。CHECK 拦住纯空白 |
| `category` | `VARCHAR(32)` | `NOT NULL`，`CHECK IN (...)` | 见 §4 |
| `color` | `VARCHAR(32)` | `NULL` | **允许为空**：用文字添加衣物时用户可能不说颜色。推荐逻辑必须能容忍缺失，而不是强行填一个假默认值 |
| `image_ref` | `VARCHAR(512)` | `NULL` | 只存**存储引用**（将来形如 `uploads/{user_id}/{uuid}.jpg` 的相对键），不存 URL、**不存二进制**。存储方案（本地盘/对象存储）待定 |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL` | 同 users |
| `updated_at` | `TIMESTAMPTZ` | `NOT NULL` | 同 users |

约束：

| 名称 | 定义 | 作用 |
|---|---|---|
| `pk_items` | `PRIMARY KEY (id)` | — |
| `fk_items_user_id_users` | `FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE` | 归属完整性 + 级联清理 |
| `uq_items_user_id_id` | `UNIQUE (user_id, id)` | **为复合外键铺路**，见 §6 |
| `ck_items_category_valid` | `category IN ('top','bottom','outerwear','dress','shoes','accessory','other')` | 类别合法性 |
| `ck_items_name_not_blank` | `length(btrim(name)) > 0` | 拒绝 `'   '` |

索引：

| 名称 | 列 | 说明 |
|---|---|---|
| `ix_items_user_id_category` | `(user_id, category)` | 「某用户的某类衣物」是最常见检索形态，如"给我所有上装" |
| `uq_items_user_id_id` | `(user_id, id)` UNIQUE | 同时充当 `user_id` 前缀索引，因此**不再单独建 `ix_items_user_id`** —— 那会变成纯冗余，只增加写放大 |

`color` 为什么不做成枚举：颜色是开放集合（"燕麦色""雾霾蓝"），枚举化会立刻不够用；
后续应由 `item_attributes` + 标签体系处理，而不是塞进主表。

`image_ref` 为什么可空：先能建档、后补图是正常流程（文字添加衣物时就没有图）。

## 4. 为什么 `category` 用 VARCHAR + CHECK 而不是原生 ENUM

| 方案 | 优点 | 缺点 |
|---|---|---|
| PostgreSQL 原生 `ENUM` | 类型安全最强，值集合固定 | **增加枚举值必须 `ALTER TYPE`**；Alembic 不会自动生成这类操作；`downgrade` 里删值几乎不可能干净回滚 |
| `VARCHAR` + `CHECK` | 加值只需重写 CHECK 约束，Alembic 能正常表达；值集合的单一事实来源在 Python 的 `ItemCategory` | 必须有 CHECK 才安全 |

衣物类别是最可能演化的字段（后续要加「内衣」「运动」「家居」）。选可演化的方案，
同时用 CHECK 保证数据库不会写入非法值。Python 侧用 `StrEnum`，CHECK 的值列表
由 `ItemCategory.values()` 生成，避免"代码里加了一个值、数据库 CHECK 忘了改"。

## 5. 已知取舍：`updated_at` 不是数据库触发器

`updated_at` 的自动更新由 SQLAlchemy 在 `UPDATE` 语句里写入 `now()`，**不是**数据库触发器。含义：

- 经 ORM 的更新：会刷新；
- 绕过 ORM 的批量 SQL、`psql` 手工改数据：**不会**刷新。

第一版接受这个取舍（少一个触发器对象，迁移更简单）。如果将来出现大量非 ORM 写入，
再加 `BEFORE UPDATE` 触发器，那是一次独立迁移。

## 6. 为什么加 `UNIQUE (user_id, id)`

这是为**将来的子表**准备的：

```sql
-- item_images 将来的形态
FOREIGN KEY (user_id, item_id) REFERENCES items (user_id, id)
```

有了它，"子行与父行属于同一用户"由数据库保证，而不是靠开发者记得加过滤条件。
单靠 `FOREIGN KEY (item_id) REFERENCES items(id)` 无法约束 `user_id` 一致，
一旦某处写错，就会产生"用户的图片挂到了别人的衣物上"这种跨用户脏数据。

## 7. 与架构文档的偏差

| 项 | 架构文档 B.3 | 本阶段实现 | 原因 |
|---|---|---|---|
| 颜色/品类位置 | `item_attributes` 子表 | 直接放 `items` 表 | 第一版只有单值颜色与单一类别，建子表属于过度设计；待需要"多属性 + 标签"时再拆 |
| 多图 | `item_images` 子表 | 单字段 `image_ref` | 同上；上传功能尚未实现 |
| 用户画像 | `user_profiles` | 未建 | 身高/体型属于推荐所需，但没有采集入口前建表等于空壳 |

## 8. 迁移

- 文件：`apps/api/migrations/versions/6efff137cb6c_create_users_and_items_tables.py`
- 版本：`6efff137cb6c`（首个 revision，`down_revision = None`）
- 已实测：`upgrade head` → 建表成功；`downgrade -1` → 两表删除仅留 `alembic_version`；
  再 `upgrade head` → 恢复；`alembic check` 报告 `No new upgrade operations detected`
  （模型与数据库完全一致）。

执行方式（**必须从 `apps/api` 目录运行**，否则读不到 `.env`）：

```bash
cd apps/api
uv run alembic upgrade head
```

应用启动时**不会**自动迁移 —— 这是刻意设计：迁移是部署动作，不是启动副作用，
多实例启动并发跑迁移会互相锁死。
