## 0. 使用说明

本文件是 WearMind 的**项目路线图与执行约束**，不是要求 Agent 一次性完成全部任务的指令。

推荐工作方式：

1. 将本文件保存到项目的 `docs/planning/` 目录，例如：
   `docs/planning/WearMind-Project-Roadmap.md`
2. 每次只让 WorkBuddy 执行一个阶段。
3. 每个阶段先阅读本文件，再执行该阶段的任务。
4. 每阶段必须先输出计划和风险，再修改文件；完成后输出验收报告。
5. 将验收报告交给另一个 Agent 独立审核；审核通过后再进入下一阶段。
6. 任何会改变远程仓库、数据库数据、系统配置或外部服务状态的操作，必须先征求用户明确同意。
7. 不允许 Agent 一次性自动执行全路线图，也不允许跳过阶段验收。

## 1. 项目目标

WearMind 是一个以个人衣橱为基础的 AI 穿搭助手。目标是逐步实现：

- 输入单件衣物照片、整套穿搭照片或文字描述。
- 管理衣物、类别、颜色、图片与基础属性。
- 基于用户衣橱和明确偏好生成穿搭建议。
- 记录穿搭历史，并在获得用户反馈后逐步改善建议。
- 支持在线模型；本地 Ollama 作为可选后备能力。
- 逐步引入 Agent 工作流，但不让 Agent 脱离真实衣物数据编造衣物 ID。
- 保护用户身份、衣橱数据、图片和偏好信息。
- 保持项目可测试、可维护、可在 Windows 11 本地开发。

**优先级：先验证技术可行性和数据安全，再扩展智能能力与产品体验。**

### 非目标与限制

- 不在早期阶段追求复杂的多 Agent 自动协作。
- 不默认上传个人衣物图片到第三方服务；必须清晰说明数据流向，并由用户选择。
- 不把模型推断出的偏好当作用户明确表达的偏好。
- 不允许 Agent 直接执行未经授权的删除、数据库重建、历史重写或强制推送。
- 不因“开发方便”而把开发身份验证机制暴露到公网。

## Phase 3：正式身份认证与授权

### 目标
建立可信身份来源，让 `UserContext` 来自服务端验证结果，而不是客户端任意声明。

### 设计前必须决定
- 仅本地单用户 MVP，还是支持多用户登录。
- 采用会话 Cookie、JWT，还是第三方 OAuth。
- 前端和 API 的部署域名、跨域与 Cookie 策略。
- 密码重置、会话过期、退出登录和账户删除的范围。
- 开发模式和正式模式配置隔离。

### 实施任务
- 先输出认证方案比较与威胁模型，等待审核。
- 选择成熟、维护中的认证实现，避免自创密码学协议。
- 将认证身份映射到数据库用户。
- 保护写操作，避免 CSRF、会话固定、令牌泄漏等风险。
- 设置安全 Cookie、HTTPS 部署要求、过期与撤销策略。
- 对认证错误返回统一且不泄漏账户状态的信息。
- 记录必要的安全审计事件，但不记录密码或令牌。
- 关闭或严格隔离开发身份注入方式。

### 验收
- 未登录不能访问受保护接口。
- 篡改用户 ID、public_id、Cookie 或 Token 不会跨用户访问数据。
- 登录、退出、过期、撤销、错误凭据都有测试。
- CORS、CSRF、Cookie、令牌存储策略有文档。
- 本地开发快捷方式不会在生产环境生效。
- 其他 Agent 独立审核认证威胁模型和关键实现。

---

## Phase 4：衣物图片与文件服务

### 目标
安全接收、保存和读取用户衣物图片。

### 实施任务
- 设计上传 API 与存储抽象。
- 验证文件大小、扩展名、MIME 与实际文件格式。
- 使用内容检测而非只信任客户端声明的 MIME。
- 随机生成存储文件名，避免路径穿越和文件覆盖。
- 限制图片尺寸、像素数和解码资源消耗。
- 评估 EXIF/GPS 等元数据的移除。
- 文件访问必须绑定当前用户的授权。
- 不允许客户端传入任意服务器文件路径。
- 设定上传限制、错误处理、删除和孤儿文件清理策略。
- 明确图片是否会发送到在线视觉模型；未获得用户选择前不得自动上传第三方。

### 验收
- 非法格式、超限文件、畸形图片均安全失败。
- 用户不能读取、替换或删除其他用户的图片。
- 存储路径不可由客户端控制。
- 文件与数据库记录的一致性有处理方案。
- 删除衣物时图片删除或保留策略明确。
- 日志不包含图片二进制、敏感路径或认证信息。

- 图片上传与预览。
- 加载中、空状态、表单校验、服务错误、重试状态。
- 前端类型与后端契约保持一致。
- 前端不得信任本地存储中的用户 ID 作为授权。
- API 地址和非秘密配置使用环境变量。
- 不在浏览器端暴露模型 API Key。

### 验收
- 主要 CRUD 流程可手工走通。
- 错误状态清楚且不会泄漏后端内部信息。
- 移动端基本布局可用。
- ESLint、TypeScript 检查和相关测试通过。
- 后端授权仍是安全边界，不能只依赖 UI 隐藏按钮。

## Phase 6：用户偏好与穿搭历史

记录用户明确表达的偏好、穿搭记录和反馈。

- 记录用户对推荐的接受、拒绝、修改及原因（可选）。
- 仅保存产品功能必要的数据，允许查看、修改、删除。

### 验收
- 用户可以查看和修改显式偏好。
- 模型推断不会静默覆盖显式偏好。
- 历史记录按用户隔离。
- 删除与保留策略清楚。
- 个人信息和偏好数据有数据生命周期说明。

## Phase 7：模型服务抽象

把业务逻辑与特定模型供应商解耦。

- 区分文本、工具调用、视觉理解能力，不按名称推断能力。

- 设置连接超时、读取超时、重试上限、并发限制与预算。
- 处理供应商限流、不可用、超时、非法 JSON。

### 验收

- 密钥不出现在前端 bundle、日志或错误信息。

## Phase 8：穿搭推荐 MVP

### 目标
基于真实衣橱数据生成可解释、可验证的推荐。

### 推荐流程
1. 认证并取得服务端用户上下文。
2. 只读取当前用户的衣物、偏好与历史。
3. 生成候选组合。
4. 模型可以负责解释、排序或补充建议，但不能随意创造衣物记录 ID。
5. 服务端校验所有引用的衣物 ID 都属于当前用户。
6. 返回推荐、理由、使用的衣物 ID、可选替代方案。
7. 保存用户反馈（经用户同意）。

### 验收
- 推荐中的每个衣物 ID 都存在且属于当前用户。
- 无衣橱数据时返回诚实的空状态或补充建议。
- 模型幻觉 ID 被拒绝或纠正。
- 推荐可追溯到具体输入与规则，但避免保存不必要的敏感提示内容。
- 推荐失败时有安全降级策略。
- 推荐效果评估有一组人工可复现样例。

## Phase 9：视觉理解

### 目标
支持单件衣物照片、整套穿搭照片和文本描述。

### 实施任务
- 明确单件衣物识别与整套穿搭解析是不同任务。
- 设计结构化输出：类别、主色、图案、材质（不确定时允许 unknown）、季节/场景（仅作为建议）。
- 模型输出必须有置信度或不确定性表示。
- 用户可修改识别结果后再保存。
- 对视觉模型做能力验证和小型评估集。
- 识别到品牌、人物、身体属性等非必要信息时不默认保存。
- 图片发送到第三方前提供清晰说明和选择。
- 不把视觉识别结果直接视为绝对事实。

### 验收
- 评估集覆盖不同光线、背景、遮挡和衣物类别。
- 模型失败、低置信度、格式错误均可恢复。
- 用户可纠正分类和颜色。
- 不支持视觉输入的模型不会被错误调用。
- 有明确数据传输和保留策略。

## Phase 10：Agent 工作流

### 目标
在受控工具、结构化状态和权限边界内编排穿搭任务。

### 实施任务
- 先画出工作流图和状态 Schema，再写代码。
- 每个工具定义输入 Schema、输出 Schema、权限与超时。
- 所有衣物工具都从服务端身份上下文确定用户范围。
- Agent 不能自行指定任意 user_id 作为授权来源。
- 对循环、最大迭代次数、超时和成本设置上限。
- 对工具调用、模型响应和最终结果做结构校验。
- 对高风险操作（删除数据、外部上传、付费调用）要求明确授权。
- 保留可追踪的执行 ID、工具名称、耗时、错误类别；不记录密钥和不必要的原始私密内容。
- Agent 的自然语言输出不得绕过后端授权和验证。

### 验收
- 状态流转、终止条件和最大步数有测试。
- 工具参数越权、伪造 ID、循环调用均被阻止。
- 模型不可用时流程可安全失败。
- Agent 输出的衣物引用全部经过后端校验。
- 其他 Agent 能根据文档独立理解工作流。

## Phase 11：历史学习与反馈闭环

### 目标
让系统利用用户反馈改善推荐，但保留用户控制权。

### 实施任务
- 区分明确反馈、行为推断和系统自动推断。
- 明确偏好更新规则、权重和可解释原因。
- 不因一次点击就断定稳定偏好。
- 提供查看、修改、撤销和删除推断偏好的能力。
- 记录推荐版本或模型版本，便于比较效果。
- 防止反馈污染、重复提交和任务重放。
- 对可能涉及敏感个人特征的推断保持克制，不主动推断健康、宗教等敏感属性。

### 验收
- 用户能查看系统记录了什么偏好及来源。
- 用户可以纠正或删除推断偏好。
- 重复反馈不会产生重复记录或不合理加权。
- 推荐改进效果可通过固定样例评估。
- 数据生命周期和用户控制能力清楚。

## Phase 12：定时任务与 Worker

### 目标
将耗时任务和定时任务从 API 进程中隔离。

### 实施任务
- 明确需要异步/定时处理的实际用例，不为了使用工具而引入任务系统。
- 定义任务状态、重试、退避、超时和取消策略。
- 使用幂等键或数据库约束防止重复执行。
- 分离 API 与 Worker 配置和启动命令。
- 避免多个 Worker 实例重复执行同一任务。
- 记录任务状态和可恢复错误，不记录敏感数据。
- 先考虑简单方案；只有需求证明后才增加队列基础设施。

### 验收
- 重试、失败、取消和重复任务均有测试。
- 任务不会越权读取其他用户数据。
- Worker 不会把秘密写入日志。
- 任务可观察、可恢复，且有资源限制。
- 定时任务有明确时区和运行策略。

## 6. 每个阶段的固定工作流

### C. 完成后

4. 扫描新增/修改内容的秘密与个人信息。

- 给出最小修复方案与可复现验证步骤。

## 8. Git、秘密与外部操作安全规则

这些规则优先级高于阶段任务中的便利性要求：

1. 默认不执行 `git push`；只有用户明确批准本次推送时才能执行。
2. 禁止 `git push --force`、`git reset --hard`、`git clean -fd`、历史重写和未经批准的删除。
3. 禁止 `git add -A` 和 `git add .`；必须使用明确的文件路径。
4. 执行提交前必须查看完整 staged diff。
5. 不输出 `.env` 内容、密码、Token、Cookie、私钥或真实数据库连接字符串。
6. 若发现疑似秘密，报告文件路径与类别即可；不要回显秘密值。
7. 不把个人照片、数据库转储、日志、备份、模型权重或本地缓存提交到 Git。
8. 不把开发身份模式暴露到公网。
9. 任何数据库删除、重建、批量更新或迁移回滚都必须先得到用户明确批准。
10. 任何安装系统软件、修改系统网络、修改防火墙或环境变量的操作都必须先征求用户同意。
11. 如果远程分支与本地历史不一致，先 fetch 并审查；不得自行覆盖远程。
12. 公开仓库按“内容会被任何人复制并长期保存”评估。

## 9. 模型与 Agent 设计原则

- 先用确定性业务逻辑解决可确定的问题，再让模型处理语义理解、排序和解释。
- 结构化输出必须经过服务端 Schema 验证。
- Agent 不能自行声明身份、任意选择用户 ID 或越过 Repository。
- 推荐中使用的衣物 ID 必须来自当前用户真实查询结果。
- 对循环次数、工具调用数、超时、并发和成本设置上限。
- 不支持视觉的模型不能接收图片任务。
- 模型输出不可信，必须当作外部输入校验。
- 模型推断偏好与用户明确偏好分开保存。
- 未经明确告知和用户选择，不要把衣物图片或个人历史发送给第三方模型。
- 失败时要有可解释的降级方案，不要假装成功。

以下事项需要在实施相关阶段前确认，不要由 Agent 擅自决定：

- [ ] 用户登录范围：单用户本地应用，还是多用户服务。
- [ ] 正式认证方式：会话 Cookie、JWT 或 OAuth。
- [ ] 衣物图片是否允许发送给在线模型，以及默认隐私模式。
- [ ] 图片本地存储位置、备份和删除策略。
- [ ] 在线模型供应商、成本预算和速率限制。
- [ ] Ollama 作为主模型还是后备模型；需以能力测试和内存测试为依据。
- [ ] 穿搭推荐的 MVP 评价标准。
- [ ] 是否采用 LangGraph，还是先用普通 Python 状态流程。
- [ ] 是否需要定时任务，以及是否需要独立 Worker。
- [ ] GitHub 仓库是否保持公开。
- [ ] 是否接受旧提交中的 Windows 用户名暴露（当前建议接受，不重写历史）。
- [ ] 是否引入 `.gitattributes` 统一换行符。
- [ ] 是否单独执行 `ruff format` 统一格式化。
- [ ] 部署目标与预算。
- [ ] 用户数据导出、删除与账号注销的要求。

## 13. 最终项目成功标准

项目只有在以下条件全部满足，才可称为 MVP 发布候选：

- [ ] 用户身份经过可靠认证，所有数据访问均有服务端授权。
- [ ] 用户能安全管理衣物、图片、偏好与穿搭历史。
- [ ] 上传和文件读取不会越权或导致路径穿越。
- [ ] 推荐只引用真实且属于当前用户的衣物记录。
- [ ] 模型调用具备超时、错误处理、预算控制与隐私告知。
- [ ] 视觉能力经过真实评估，不按模型名称猜测。
- [ ] Agent 工具调用有权限、Schema、循环和成本限制。
- [ ] 反馈学习可查看、修改、撤销和删除。
- [ ] 核心单元、集成、端到端和安全测试通过。
- [ ] 新环境安装、数据库迁移、备份恢复均可复现。
- [ ] 日志、Git 历史和发布文件完成秘密与个人信息审查。
- [ ] 所有重大剩余风险均已记录，并由项目负责人明确接受。
